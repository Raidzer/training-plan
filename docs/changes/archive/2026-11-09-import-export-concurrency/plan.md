# Параллельный импорт и экспорт дневника и плана

Статус: выполнено
Ветка: `perf/import-export-concurrency`

## Области и источники

- Серверные операции плана, дневника, отчётов, веса и восстановления.
- HTTP API `/api/plans/import`, `/api/diary/import`, `/api/diary/period-export`.
- Актуальное поведение: [импорт и экспорт](../../../spec/import-export.md).
- Связанные гарантии сохранения отчётов и порядка блокировок:
  [архив обуви](../../../spec/shoes-archive.md).

## Цель и границы

Сохранить текущий сценарий загрузки и скачивания Excel, уменьшить общую нагрузку
при одновременной работе пользователей и устранить выявленные гонки импорта.
Обычные запросы не должны конкурировать с неограниченным числом тяжёлых операций.

Не входят: новые зависимости и инфраструктура, фоновые задания с отдельным
интерфейсом, worker-процессы, изменение формата Excel, удаление старых дублей,
глобальное изменение таймаутов всех сервисов и настройки внешнего прокси.

## Требования

Подтверждено пользователем:

- Сохраняются существующие формы импорта и скачивание файла в текущем интерфейсе.
- Пока запрос ожидает или обрабатывается, кнопка заблокирована и показывает загрузку.
- Ожидание свободного места в очереди — до 60 секунд; затем показывается понятная
  ошибка с предложением повторить. Это не ограничение времени обработки файла.
- Максимальный файл — 10 МиБ, максимум 10 000 строк на импорт, период экспорта —
  не более 20 лет. Превышение возвращает понятную ошибку, данные не записываются.

Общее решение подтверждено пользователем 2026-11-09:

- Общая для трёх XLSX API очередь в каждом процессе Next.js: две активные операции
  и до 20 ожидающих. Переполненная очередь отвечает сразу; автоматического повтора нет.
- Авторизация выполняется до очереди, разбор multipart и Excel — после получения
  места. Фактически прочитанный размер тела ограничен с учётом multipart overhead.
- Отключившийся ожидающий запрос удаляется из очереди. Место активной операции
  освобождается после её фактического завершения, включая ошибку.
- При повторном импорте плана существующие даты пропускаются целиком. При импорте
  дневника дни с отчётом, весом или восстановлением пропускаются целиком. Параллельная
  обработка сохраняет те же правила; существующие данные не перезаписываются импортом.
- Проверка и запись выполняются под общей транзакционной блокировкой данных
  пользователя. Эту же блокировку используют обычные записи плана, отчёта, веса
  и восстановления, включая вызовы из ботов, а также административная очистка
  этих данных. Повторная проверка даты отчёта под блокировкой предотвращает запись
  на устаревшую дату после сдвига плана. Пользователи не блокируют друг друга.
- Импорт остаётся атомарным. Запись выполняется пакетами, без утраты последовательной
  семантики нескольких тренировок одного дня. Счётчик отчётов отражает реальные вставки.
- Экспорт получает строки, недельные итоги и данные листа «Человек» из одного
  согласованного снимка БД; построение XLSX происходит после завершения чтения.

## Технические решения и последствия

- Общий процессный singleton очереди хранится в `globalThis`, чтобы разные серверные
  bundles маршрутов разделяли состояние. При нескольких экземплярах приложения
  лимит умножается на их число. Это ограничитель работы, не долговечная очередь заданий.
- Межпроцессная согласованность записей обеспечивается PostgreSQL advisory lock
  по пользователю, взятым до существующих блокировок строк плана и обуви. Новые
  таблицы, уникальные индексы и миграции не требуются; старые дубли не исправляются.
- Размер SQL-пакета ограничен. Повторные ключи веса и восстановления внутри файла
  объединяются до bulk INSERT с сохранением результата последовательного импорта.
- Ожидание соединения пула и блокировки ограничено пятью секундами; ожидание
  блокировки задаётся локально в участвующих транзакциях. Общий timeout выполнения
  SQL для всех сервисов не вводится. Сам размер пула не увеличивается.
- Ограничение 10 000 строк проверяется и для листа, и после разбиения строки
  плана на отдельные тренировки. Полный экспорт истории длиннее 20 лет возвращает
  ошибку с предложением выбрать меньший период; молчаливое усечение запрещено.
- Чтение экспорта выполняется в короткой `REPEATABLE READ READ ONLY` транзакции.
  Сервисы получают существующий транзакционный query executor; обычные вызовы
  продолжают использовать `db` по умолчанию.
- Ограничение числа операций уменьшает конкурентное потребление памяти и БД,
  но не переносит синхронную обработку Excel с основного JS-потока. Лимит сжатого
  файла не равен пределу распакованной книги. Жёсткая изоляция CPU/RAM одной книги
  потребовала бы отдельного решения.
- Внешний прокси может оборвать HTTP-запрос раньше приложения. Его фактические
  настройки недоступны из репозитория; 60 секунд ожидания требуют дополнительного
  времени на загрузку и обработку.

      три XLSX API. Проверить общий предел, FIFO, заполнение очереди, таймаут, отмену,
      освобождение после ошибки, ограничения реального тела, файла, строк и периода.
- [x] 2. Согласовать конкурентные записи через общую блокировку пользователя.
      Перенести проверки существующих дней в транзакции импорта, выполнить пакетную
      запись и сохранить итог нескольких тренировок одного дня. Проверить отсутствие
      дублей и перезаписи при двух импортах и при импорте одновременно с ручным сохранением,
      независимость пользователей, корректность счётчиков и полный rollback при ошибке.
- [x] 3. Перевести чтение экспорта на единый снимок. Проверить согласованность строк
      и недельных итогов при параллельном изменении, прежний формат и порядок листов,
      сохранение диапазона полной выгрузки и границы 20-летнего периода.
- [x] 4. Обновить актуальную спецификацию и навигацию, провести независимое ревью,
      выполнить lint, type-check, test:coverage, build и изолированные PostgreSQL-проверки.
      Зафиксировать фактические результаты; архивировать только завершённое изменение.

Пользователь подтвердил выполнение всех четырёх этапов подряд с проверкой
и отчётом по каждому, без отдельного запроса разрешения между этапами. Обычные
технические решения принимаются автономно; изменение требований и границ
возвращается на согласование.

## Проверки и текущее состояние

- До реализации профильные тесты исходного состояния: 13 файлов, 122 теста успешно.
- План подтверждён, реализация начата.
- Первоначально Docker daemon был недоступен. Docker Desktop запущен, для
  PostgreSQL-проверок создан одноразовый контейнер на `127.0.0.1:55432`,
  вне рабочей БД. После проверок контейнер и временные схемы удалены.
  Интеграционные проверки использовали явные тестовые реквизиты, без `.env`.
- Независимая проверка дизайна выявила необходимый охват обычных записей и
  объединение повторных ключей перед bulk INSERT; эти требования включены выше.
- Проверка интеграции нашла гонку записи сна через Алису: прежнее чтение
  восстановления до блокировки могло перезаписать флаги нового импорта.
  Исправлено: Алиса передаёт только сон; сервис сохраняет остальные поля
  под общей блокировкой. Повторная проверка на PostgreSQL подтвердила результат.
- Первая общая проверка: 230 файлов / 1799 тестов успешно; покрытие
  statements 88,48%, branches 82,04%, functions 87,81%, lines 88,97%.
  Type-check и production build успешны. После исправления замечания ревью
  общие проверки будут повторены.
- Независимо выполнены 22 PostgreSQL-проверки: 8 для импортов/снимка экспорта,
  14 для обычных writers, даты отчёта, записи сна, timeout и rollback.
