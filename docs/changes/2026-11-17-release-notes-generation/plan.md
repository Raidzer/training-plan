Статус: в работе

Ветка: `fix/release-notes-generation`

## Цель и границы

Убрать дубли и технические подписи в автоматически создаваемых патч-ноутах.
Пользователь согласовал весь план и автономное выполнение 17 ноября 2026 года.
Затронуты подготовка релизного PR в `.github/workflows/ci.yml`, скрипты и тесты

Спецификация области после реализации: [Описание релиза](../../spec/release-notes.md).

Уже опубликованные релизы, история changelog, UI, вычисление версии, публикация
Docker-образов и GitHub Release остаются вне задачи. Новых зависимостей нет.

## Согласованные требования и критерии приёмки

- Источник пункта — только заголовок объединённого MR (PR в GitHub), вошедшего
  в диапазон нового релиза. Сообщения и описания отдельных коммитов не используются.
- Один MR не создаёт повторные пункты, даже если у него несколько коммитов
  и отдельный merge-коммит.
- Сохраняются разделы из `release-please-config.json`: «Новое», «Исправления»,
  «Внешний вид». Тип заголовка определяет раздел; скрытые технические типы не выводятся.
- В пункте остаётся текст заголовка без типа, scope (`diary`, `profile` и других),
  служебных номеров MR и хешей коммитов. Например,
  `feat(diary): показывать пробег обуви при выборе в тренировке` превращается
  в `показывать пробег обуви при выборе в тренировке`.
- CHANGELOG и тело подготовленного релизного PR содержат одинаковый текст
  новой версии. Старые разделы CHANGELOG сохраняются без изменения.
- Прямые коммиты, открытые MR и MR предыдущих релизов не становятся пунктами.
  Служебный PR Release Please не становится пользовательским изменением.
- Ошибки GitHub API и некорректный/пустой результат останавливают подготовку
  с понятной ошибкой. Повторный запуск не создаёт лишних изменений.

## Технические решения

Release Please по-прежнему готовит версии, manifest и релизный PR. Дополнительный
шаг получает коммиты между предыдущим выпуском (либо `bootstrap-sha` при первом)
и проверенным SHA `main`, находит связанные объединённые PR и формирует пункты
из их заголовков. Это учитывает feature PR, объединённые через `develop` и релизную
ветку обычными merge-коммитами. Изменяется только тело новой версии в CHANGELOG
релизной ветки и соответствующий фрагмент body PR. Запись файла использует текущий
blob SHA, чтобы конфликтующее обновление не перезаписалось молча.
