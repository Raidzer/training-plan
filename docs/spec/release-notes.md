# Описание релиза

## Источник и потребители

`src/releases/CHANGELOG.md` содержит описание версии для окна «Что нового» и
GitHub Release. Приложение выбирает раздел установленной версии, а публикация
читает тот же раздел на проверенном SHA релизного PR. Описание опубликованного
релиза и прежние разделы changelog автоматически не переписываются.

## Подготовка будущего релиза

Release Please вычисляет версию по Conventional Commits и создаёт/обновляет
релизный PR в `main`. Следующий шаг workflow заменяет автоматически подготовленный
текст новой версии описанием из заголовков объединённых MR (PR в GitHub).

В диапазон входят коммиты между предыдущим выпуском и проверенным SHA `main`.
Для первоначального выпуска используется `bootstrap-sha`, для явно заданной
границы — `last-release-sha`. Связанный MR включается, только если он объединён
и его merge/squash SHA входит в этот диапазон. Это учитывает MR в `develop`
и релизные ветки, чья история сохранена при объединении в `main`.

Каждый MR создаёт один пункт независимо от числа коммитов. Текст сообщений
и описаний отдельных коммитов не используется. Открытые MR, прямые коммиты,
изменения прежних релизов и служебные MR Release Please исключаются.

Тип заголовка определяет раздел согласно `release-please-config.json`:

| Тип | Раздел |
| --- | --- |
| `feat` | Новое |
| `fix` | Исправления |
| `style` | Внешний вид |

Скрытые и неуказанные типы не выводятся. Из текста убираются тип, необязательный
scope и breaking-маркер, а также служебные суффиксы вида `(#123)` и `(728a871)`.
Например, `feat(diary): показывать пробег обуви` становится пунктом
`показывать пробег обуви` в разделе «Новое». Непустые разделы сохраняют порядок
из конфигурации; пустые разделы пропускаются.

## Запись и ошибки

Меняется только новая версия в релизной ветке: её заголовок, прежняя история
и переводы строк сохраняются. Такой же текст записывается в body релизного PR.
Запись changelog использует исходный blob SHA; конфликт не перезаписывается молча.
Повторный запуск с уже подготовленным текстом не создаёт лишних записей.
Если Release Please при повторе не вернул номер PR, генератор находит единственный
открытый PR в `main` из того же репозитория с меткой `autorelease: pending`.
Отсутствие кандидатов завершает шаг без записей, несколько кандидатов дают ошибку.
После успешной записи файла и сбоя обновления body повтор завершает синхронизацию
без дополнительного коммита. Несовпадение SHA основной ветки PR с проверенным
SHA запуска CI останавливает обработку до записей.

Ошибка API, отсутствие подходящих MR, пустое описание, отсутствующая или
неоднозначная версия, некорректный manifest или неподходящий релизный PR
останавливают подготовку с ошибкой. Сообщения коммитов не служат запасным
источником пользовательского описания.

## Проверяемые сценарии

- MR с двумя коммитами и отдельным merge даёт один пункт из title MR.
- MR после squash даёт такой же пункт, если squash SHA входит в диапазон.
- MR через `develop` и релизную ветку включается при сохранённой истории.
- Scope `diary`, `profile` и прочие, номера MR и SHA не становятся подписями.
- Новый раздел одинаков в changelog и body; предыдущие версии остаются прежними.
- Пустой результат и сбои API не превращаются в описание из коммитов.
- Повтор без нового output Release Please находит существующий PR и завершает
  прерванное обновление. Продвинувшийся `main` не приводит к неполному описанию.

Проверки: `tests/scripts/release/generateReleaseNotes.test.ts`,
`tests/scripts/release/updateReleasePullRequest.test.ts` и существующие тесты
чтения и публикации релиза. Облачная проверка интеграции выполняется после
попадания workflow в `main`.
