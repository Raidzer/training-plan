# Training Plan

**Training Plan** — это современная платформа для планирования и анализа беговых тренировок. Приложение помогает спортсменам вести дневник, анализировать прогресс и использовать полезные инструменты для расчетов.

🚀 **Production:** [swarm-protocol.ru](https://swarm-protocol.ru)

---

## 🛠 Технологический стек

Проект построен на современном стеке технологий, обеспечивающем высокую производительность и удобство разработки.

### Frontend

- **Framework:** [Next.js 16](https://nextjs.org/) (App Router)
- **Language:** [TypeScript](https://www.typescriptlang.org/)
- **UI Library:** [Ant Design 6](https://ant.design/)
- **Styling:** CSS Modules / SCSS
- **State/Form:** React Hook Form / local state

### Backend & Database

- **API:** Next.js API Routes (Serverless functions)
- **Auth:** [NextAuth.js](https://next-auth.js.org/)
- **Email:** Nodemailer 10 подключён через npm-алиас `smtp-mailer`: optional peer
  NextAuth 4 ограничен Nodemailer 7. Авторизация использует только Credentials;
  встроенный Email provider и общий импорт `next-auth/providers` требуют отдельного
  решения по совместимости.
- **Database:** PostgreSQL
- **ORM:** [Drizzle ORM](https://orm.drizzle.team/)

### Infrastructure & Tools

- **Containerization:** Docker & Docker Compose
- **Bot:** [GrammY](https://grammy.dev/) (Telegram Bot integration)
- **Linting:** ESLint, Prettier, Husky (pre-commit hooks)
- **Testing:** Vitest

### Production-образ

Сборка использует полное дерево зависимостей. Отдельная стадия `production-deps`
удаляет dev-пакеты через `npm prune --omit=dev`; конечный образ получает только
сокращённое дерево. Линтер и тестовый runner в production-образ не входят.

`dotenv` и `tsx` входят в production-зависимости: они нужны для ожидания БД,
миграций, seed и запуска ботов. Optional-зависимости сохраняются для native
модулей; часть пакетов, объявленных как dev, может оставаться через peer-связи
production-зависимостей. Сокращение образа не исправляет код внутри bundles Drizzle.

### Исправления вложенных зависимостей

В `package.json` закреплены адресные npm overrides для существующих зависимостей:

- `exceljs -> uuid 11.1.1` исправляет проверку границ буфера и сохраняет
  CommonJS-вызов `uuid.v4()`, используемый ExcelJS для расширенного форматирования.
- `drizzle-kit -> @esbuild-kit/core-utils -> esbuild 0.25.12` устраняет
  открытый CORS локального esbuild-сервера и сохраняет TypeScript-трансформации.

Overrides нужны, пока родительские пакеты требуют уязвимые версии. При обновлении
ExcelJS или Drizzle проверьте их диапазоны и фактическое дерево `npm ls`; удаляйте
соответствующее закрепление после проверки XLSX и команд Drizzle с исправленными
версиями upstream. Overrides не заменяют код внутри bundle-файлов Drizzle-kit
и браузерного bundle ExcelJS.

## ✨ Основные возможности

- 📅 **Дневник тренировок:** Удобное отображение плана и факта тренировок, интеграция с календарем.
- 📊 **Аналитика:** Детальный анализ выполнения заданий, учет объема и интенсивности.
- 📥 **Импорт планов:** Возможность загрузки тренировочных планов из Excel файлов.
- **Личные рекорды из соревнований:** После сохранения результата на стандартной дистанции можно сразу подтвердить первый или улучшенный рекорд. Переносятся время, дата и название забега; прежние город и протокол очищаются. Пропуск сохраняет забег, а последующее изменение или удаление забега не меняет рекорд.
- 🧮 **Инструменты:**
  - **Калькулятор темпа:** Расчет темпа на дистанции, прогноз результатов.
  - **Конвертер скоростей:** Перевод км/ч в мин/км и другие единицы.
- 🤖 **Telegram Бот:** Уведомления и взаимодействие с платформой через мессенджер. На следующий день после соревнования бот запрашивает результат в настроенное время рассылки: можно отметить пропуск или внести время, а новый личный рекорд сохранить отдельной кнопкой.

## 🚀 Запуск проекта

### Предварительные требования

- [Node.js](https://nodejs.org/) 24.22.1 LTS (версия закреплена в `.nvmrc`; поддерживается Node 24 начиная с 24.22.1)
- [Docker Desktop](https://www.docker.com/products/docker-desktop/) (для запуска БД)

### Установка и запуск

1.  **Клонируйте репозиторий:**

    ```bash
    git clone https://github.com/raidzer/training-plan.git
    cd training-plan
    ```

2.  **Установите зависимости:**

    ```bash
    npm install
    ```

3.  **Настройка окружения:**
    Создайте файл `.env` в корне проекта (сиспользуйте пример из `.env.example`, если есть, или запросите конфигурацию).

4.  **Запуск базы данных (PostgreSQL):**

    ```bash
    npm run db:up
    ```

5.  **Инициализация (Миграции и Seed):**

    ```bash
    npm run dev:init
    ```

    _Эта команда запустит контейнер БД, подождет его готовности, применит миграции и заполнит базу тестовыми данными._

6.  **Запуск в режиме разработки:**
    ```bash
    npm run dev
    ```
    Приложение будет доступно по адресу [http://localhost:3100](http://localhost:3100).

## Выпуск версии

Описание для окна «Что нового» и GitHub Release хранится в
`src/releases/CHANGELOG.md`. Вручную повышать версию приложения не нужно.

1. Объедините подготовленные изменения в `main`. Используйте Conventional Commits:
   `feat(...)` для новых возможностей, `fix(...)` для исправлений и `style(...)` для
   визуальных изменений. Тип и необязательный scope пишите на английском, описание —
   на русском, как понятное пользователю изменение для changelog, например
   `feat(plan): добавлен поиск тренировок`. При squash merge проверьте итоговый заголовок коммита.
2. После успешных lint, type-check, тестов с покрытием, сборки и Docker-публикации
   Release Please откроет или обновит релизный PR в `main`. Первый выпуск — `1.3.0`;
   история до предыдущего выпуска `3fc64f4` исключена. Следующие версии вычисляются
   по коммитам.
3. Дождитесь завершения набора изменений и отредактируйте русский текст в
   `src/releases/CHANGELOG.md` релизного PR. Проверьте также версии `package.json`,
   `package-lock.json` и `.release-please-manifest.json`. Новое обновление PR ботом
   может перезаписать ручную редактуру, поэтому проверяйте окончательный diff перед merge.
4. Объедините релизный PR. Его SHA проходит CI; затем публикуется образ с тегом
   `v<версия>` для `linux/amd64` и `linux/arm64`, после него — Git-тег и GitHub Release.
   Текст публикации берётся из файла на этом SHA. Редактировать body PR для синхронизации
   описаний не требуется. До успешного завершения CI и Docker релиз не публикуется.

Обычные сборки используют версию `<package-version>-<короткий-SHA>` и Docker-тег
`sha-<короткий-SHA>`. Релизный образ получает чистую версию и тег `v<версия>`.
Плавающий тег `main` обновляется только для актуального SHA основной ветки. Ручной
запуск Docker и сборка по Git-тегам `v*` остаются доступны; автоматический выпуск
вызывает Docker напрямую, поскольку события от `GITHUB_TOKEN` не запускают новую цепочку.

Для автоматики используется встроенный `GITHUB_TOKEN`, без PAT. В настройках
репозитория **Settings → Actions → General** разрешите **Allow GitHub Actions to create
and approve pull requests**. Созданный ботом PR может потребовать ручного **Approve
workflows to run**; если CI не запустился, проверьте вкладку Actions перед объединением.
Workflow должен сначала попасть в `main`; создание PR и реальная публикация проверяются
первым облачным прогоном.

При ошибке повторите исходный запуск CI или его упавшие задания через **Re-run jobs**.
Автоматика сохраняет исходные SHA, версию и описание. Совпадающие тег, Release и образ
переиспользуются; при частично завершённом выпуске она допубликует Release и обновит
метки PR. Ошибки сети и доступа не считаются отсутствующим образом. Конфликт SHA или
текста останавливает выпуск: проверьте опубликованные данные и причину расхождения,
не перемещайте существующий релизный тег. Старый запуск не откатывает Docker-тег `main`.
